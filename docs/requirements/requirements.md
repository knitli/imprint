**Status:** Working requirements for discussion, not legal advice or an authorization to operate  
**Date:** November 4, 2026  
**Adopted project names:** OpenSCG (open schema and specification) and Imprint (authoring/management application). Trademark and domain clearance remain outstanding.  
**Audience:** SCG authors, original classification authorities (OCAs), security and classification policy staff, developers, and prospective adopters.

**Related analysis:** [Git versioning and Defense Unicorns UDS addendum](scg-git-uds-addendum.md) gives supporting detail. This requirements document controls where the earlier addendum differs.

## 1. Decision and objective

Build **OpenSCG**, a public, independently governable JSON Schema and semantic specification for structured security classification guides (SCGs), and **Imprint**, an open, self-hostable reference application for creating, validating, signing, and exporting guides. OpenSCG is maintained in its own repository and published as its own package; it is usable without Imprint. Imprint consumes and implements a stated OpenSCG version. The first public release must be useful with synthetic, unclassified data and credible enough to solicit feedback from classification professionals. Its purpose is to help humans author and communicate classification guidance; it does not itself grant original classification authority or make classification and release decisions.

The proposed format is independent of any undisclosed DTIC template or schema. If an authoritative government format becomes available, map it through a documented adapter or revise the format deliberately; do not claim equivalence beforehand. This project may supply a component relevant to ACME Function 1 as described in the earlier discussion, but it is not an integrated DoD-wide system, official government standard, or replacement for DTIC. The specific ACME statement has not been independently verified here.

**Release boundary:** a single-user, local/self-hosted authoring workflow, with a signing path that reuses an existing approved, configured PKI credential and browser/workstation signing capability, and JSON, PDF, and XLSX outputs. Public demo data is synthetic only. Signing is in scope for MVP. Credential issuance, provisioning, token enrollment and middleware installation are outside project scope; identifying the already-approved signing interface and obtaining a representative test environment are release dependencies.

### Success

An SCG practitioner can create a representative synthetic guide, see actionable completeness checks, sign a frozen revision with an existing approved test credential through the supported browser/workstation path, export matching representations, verify the approval, and provide meaningful feedback. An independent developer can validate and read the JSON using only the published specification and test fixtures. Collect qualitative feedback from SCG authors and policy personnel; do not substitute downloads or stars for that feedback.

## 2. Evidence and obligations

### The FY2025 ISOO findings

The official [ISOO FY2025 Annual Report, pp. 6–8](https://www.archives.gov/files/isoo/reports/isoo-fy-2025-annual-report-final-508.pdf) reports six agency inspections and ten SCGs reviewed, and an **82.5% average agency SCG score**. Three guides at three agencies failed to map classification levels to specific elements; one lacked required declassification dates or events; and three guides at three agencies lacked specific classification reasoning. These are observations from this review, not estimates of government-wide prevalence. ISOO also identified missing or fragmented guidance at two agencies and warned of inconsistent decisions.

**Product response:** require explicit elements, levels, rationale and declassification instructions before approval; identify missing guidance without pretending a software check proves its correctness; support clear references and later review. The report also notes [ISOO Notice 2025-01](https://www.archives.gov/files/isoo/notices/isoo-notice-2025-01-automatic-declassification-exemption-incorporation-notice-508-complete.pdf), which addresses the conditions for incorporating approved automatic-declassification exemptions into SCGs. A code picker alone cannot establish the required approval and notice.

## 3. Users, boundaries, and primary workflow

**Author:** enters guidance, edits a draft, resolves validation findings, and generates preview artifacts. **OCA/approver:** reviews the exact revision and exercises their own authority. **Consumer:** finds and reads an issued guide, verifies provenance, and uses its guidance in an authorized environment. **Administrator:** configures a local installation and trust policy; MVP is not a shared enterprise administration system.

1. Start a draft or import a supported OpenSCG JSON file; enter guide details, document markings and information-element guidance.
2. Add classified, unclassified, conditional, and compilation entries in plain language. Record applicable controls, source references and explanatory notes.
3. Validate. Errors identify the exact field and block an approval operation; warnings require human review. A draft can be saved with errors.
4. Preview complete PDF and mapped XLSX alongside JSON, including warnings and an explicit **DRAFT / NOT APPROVED** label on draft outputs.
5. Freeze a candidate revision, generate its canonical digest, display its identity and approval statement. An OCA uses the existing approved credential and supported browser/workstation signing interface to sign after reviewing the candidate.
6. Verify the signature and trust chain, record OCA delegation evidence as a separate human-reviewed claim, and export the revision and associated signed attestation. Issuance/distribution is an organizational act; the software never asserts it happened merely because a signature exists.
7. Reopen and verify exports. A content change creates a new draft revision and invalidates the prior approval for the changed content; preserve prior approved artifacts.

**MVP excludes:** collaborative review and task routing, a shared registry, DTIC submission or synchronization, semantic/vector search, AI classification, fully automated rule execution, live SharePoint integration, XLSX import, and full AEA support. Basic draft persistence and human-readable revision identifiers are in scope. A catalog, sharing, integrations and richer import are sequenced below.

## 5. OpenSCG: schema, specification, and governance

OpenSCG is the public format and specification, maintained in a separate repository and distributed as its own package; Imprint is one implementation and consumes a released OpenSCG version. Neither project is an official government standard. OpenSCG's maintenance, releases and conformance do not depend on using Imprint, its database, UDS or Git.

### Model and semantic contract

The public schema is a **proposed open interchange format**, not an official standard. Use a stable schema URI, explicit `schema_version`, documented version compatibility and migration rules. Specify syntax using JSON Schema 2020-12 and use a separate semantic specification and validation profile for cross-references and conditional rules. An extension namespace must preserve names and values; unknown extensions are not assumed safe to ignore for approval or deterministic interpretation.

Minimum conceptual fields:

- **Guide:** `guide_id`, `revision_id`, schema/profile versions, title, scope, issuing organization, contact, OCA identity/position or identifier, issue/last-review/effective dates, lifecycle state and supersession links when known.
- **Document protection:** SCG classification, control/portion markings, classification authority block, and provenance distinct from the rules it contains. Markings must be reviewed by an authorized person.
- **Entries:** stable `entry_id`, descriptive information element, level, conditions and exceptions, controls and release restrictions, concise rationale plus zero or more §1.4 categories as appropriate, declassification instruction and authority reference, source links, and optional value/damage/unclassified explanatory statements.
- **Compilation:** human-readable triggering conditions, constituent entry references where meaningful, resulting protection, rationale and declassification. Conditions may be narrative; do not encode narrative as an executable rule unless explicitly supported and tested.
- **Authority and history:** claimed signer identity, program/level of claimed delegation, approval statement and supporting reference; record that independent authority review is pending or complete. Link prior revisions and supersession/cancellation events without making current validity assumptions from old records.
- **Extensions:** namespaced supplemental data and its must-understand behavior; define which data affects hashes and signatures. Do not use an extension mechanism to bypass profile requirements.

### Canonicalization, artifacts and fidelity

Define an exact signed payload version: canonical JSON serialized with [RFC 8785](https://www.rfc-editor.org/rfc/rfc8785), UTF-8 encoded, with a documented top-level set of included fields. Reject duplicate member names, nonconforming numbers and inputs that cannot be represented under the canonicalization rules. Compute SHA-256 over those exact bytes. Store the digest algorithm and payload-format version; never include the signature or digest in the bytes being digested. Approval statements bind purpose, guide ID, revision ID, digest algorithm/value, profile and signer context; the exact byte encoding and domain separation must be specified before implementation. Do not normalize or rewrite signed content after signing.

The PDF and workbook display the guide ID, revision and canonical payload digest; their file hashes differ and the digest alone does **not** prove either rendition faithfully matches the signed JSON. Generate both from the frozen revision and test mappings. Bundle the signed JSON and detached attestation with the PDF/XLSX. For tamper evidence of a specific PDF or workbook, independently sign or include their final byte hashes in a separate signed release manifest, avoiding recursive hashes. If a native PDF signature is added, clearly distinguish it from the canonical JSON attestation. Consumer instructions must state what was checked.

The XLSX export is a documented mapping and a preliminary interoperability bridge. Preserve textual guidance, headings, controls and compilation/threshold data within the supported profile. Publish a coverage matrix and a loss report. DoDM's required submission format and DTIC template compatibility must be validated against the authoritative template and responsible office before claiming conformance. A generic workbook is not a DTIC submission. An importer, when added, must handle hostile files and refuse ambiguous mappings.

## 6. Signing design and security contract

### Scope and existing environment

Imprint is a **relying application**. It does not issue or provision credentials, configure browser crypto modules, enroll tokens, issue certificates, install middleware or operate PKI. Assume the organization has already supplied its approved credential, trust chain, cryptographic middleware and browser configuration. Imprint must work with the supported environment's existing signing interface, with hardware-backed or software-backed credentials as its policy permits; the application does not assume token physical form from the classification of a network.

The project owner reports that relevant DoD users already have browser-configured certificates and PKCS#11 modules, with CAC/PIV-style credentials on unclassified systems, distinct credentials on SIPRNet and software credentials in some TS environments. [DoDI 8520.02](https://www.cac.mil/Portals/53/Documents/DoDI-8520.02.pdf), enclosure 3 §1, describes CAC use on NIPRNet and SIPRNet hardware-token support. A [DoD unclassified Firefox guide](https://dl.dod.cyber.mil/wp-content/uploads/pki-pke/pdf/unclass-config_firefox_utilize_dod_cac.pdf) describes configuring a CAC PKCS#11 module. Public sources examined do not establish one universal TS configuration; confirm the target environment with its owner. [NIST FIPS 201 key management](https://pages.nist.gov/FIPS201/keymanagement/) distinguishes authentication, digital-signature and key-management certificates. NIST 800-53 control applicability depends on the system baseline and implementation; do not claim it universally mandates a particular browser PKCS#11 interface or that every credential is available for document signing.

### Browser handshake: discovery before implementation

A configured certificate can support browser client-certificate authentication without giving an ordinary web page direct access to the same private key for arbitrary document signatures. Standard WebCrypto can perform signing when a usable `CryptoKey` is exposed to the page, but does not define a portable way for a site to enumerate an existing browser PKCS#11 module and obtain its private key. [W3C WebCrypto](https://www.w3.org/TR/webcrypto/). Mozilla's [`pkcs11` extension API](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/pkcs11) manages access to modules and does not itself specify an arbitrary-document signing function; Chrome's [`platformKeys` extension API](https://developer.chrome.com/docs/extensions/reference/api/platformKeys) is documented as ChromeOS-only, not a general Chromium desktop interface. Browser/OS and enterprise configuration matter.

**Required first investigation:** for the actual supported Chromium-based and Firefox installations, identify any existing agency-approved document-signing service, extension, browser integration or local application, its interface and supported signature format. Trace a synthetic request end to end with an already configured credential. Determine separately whether plain page JavaScript can obtain a usable key and call a signing operation; do not infer that from successful client-certificate login. Prefer reusing the existing approved interface. If it cannot supply a document-signing operation, evaluate an already-approved native/extension bridge or external signer and document deployment implications; a newly installed bridge is not presumed necessary or in scope without a separate decision.

### Required signing transaction

1. **Freeze and review:** validate a candidate, compute the canonical payload and SHA-256 digest, and show the complete guide, revision, approval statement and signer context. Explicit approval is required for this exact content.
2. **Request:** send the specific versioned approval statement, digest algorithm and bytes or digest as required by the approved interface, together with purpose and request identifier. The selected signing interface must make the identity, scope and meaningful confirmation available; do not send arbitrary unbound requests. Work out the exact message protocol and certificate/key selection from the selected environment rather than inventing a browser API.
3. **Sign:** the existing approved browser/OS integration uses an appropriate digital-signature credential and handles any PIN or confirmation. Imprint never asks for, captures, stores, transmits or logs a PIN or private key. An authentication certificate is not automatically suitable for document signing.
4. **Return and verify:** receive the signature and necessary public certificate/chain data. Package a versioned detached CMS attestation over the specified approval statement, or document an equivalent organization-approved format; establish which component constructs signed attributes and which bytes are passed to the token to prevent double hashing or signing the wrong input. Independently verify the exact binding, permitted algorithm, key usage/policy, chain and time/revocation status under local policy. Record unknown/offline status explicitly and fail according to the policy. A signer-provided timestamp is not automatically trusted.
5. **Authority and preservation:** independently verify the signer's OCA delegation, program scope, level and agency acceptance of the signature process. Preserve the prior signed bytes and verification evidence; changing protected content requires a new signed revision. Signing does not itself issue or distribute the guide.

An existing approved PDF-signing application is an alternative if the browser integration cannot produce the needed attestation. A PDF signature proves the signed PDF bytes, not automatically the JSON or XLSX; establish and verify a common-revision binding before claiming otherwise. [RFC 5652](https://www.rfc-editor.org/rfc/rfc5652.html) defines CMS, [RFC 5280](https://www.rfc-editor.org/rfc/rfc5280.html) defines X.509 path validation, and [ETSI PAdES](https://www.etsi.org/deliver/etsi_en/319100_319199/31914201/01.02.01_60/en_31914201v010201p.pdf) covers PDF signatures. Use a mature implementation; do not hand-build CMS/DER or PDF byte ranges.

**Signed MVP acceptance:** demonstrate signing and independent verification with at least one representative agency-approved, preconfigured browser/workstation and credential, test altered payload and trust/revocation failure cases, and document the supported matrix and agency acceptance process. Chromium and Firefox are target browser families, not a claim that both are qualified at initial release; test each intended configuration before claiming support. If a representative environment is unavailable, release an explicitly unsigned synthetic preview and keep signing as an open signed-MVP gate.

## 7. Security, privacy, and deployment constraints

- **Security boundary:** public demo is for synthetic data; no classified or controlled data in an unapproved environment. Self-hosted use for real information requires the system, network, operators, storage, backups, integrations and transfers to be authorized for the data and applicable controls. Packaging is not an ATO, accreditation, or a cross-domain solution.
- **Local-first default:** do not send guide contents, metadata, certificate material or telemetry externally by default; disable third-party fonts/scripts, hosted analytics and remote error reporting. Provide a network inventory and an offline installation route using organization-approved packages and images.
- **Data protection:** enforce deployment-appropriate authentication and authorization if multi-user or network-accessible; restrict file and backup access, encrypt in transit/at rest where required, isolate tenants and classification domains, define retention and secure disposal with the operator. Avoid logging guide text, secrets, PINs or sensitive metadata. Local browser storage alone is not a security boundary.
- **Untrusted input:** validate JSON and eventual workbook uploads on the server/trusted process, enforce size/depth/time limits, safe parsing, output escaping and resource limits. Disable external document references and formulas; neutralize spreadsheet formula injection in exported untrusted text. Do not execute imported macros or embedded content. A client-side dropdown or workbook cell validation is not an enforcement boundary.
- **Signing trust:** assess the chosen existing signing interface against malicious websites, request substitution and signing-oracle abuse. Apply origin/permission controls, a protected channel where applicable, human review, content and purpose binding, and defined failure states. If a bridge is used, review its local process identity and channel; test the actual interface and threat model.
- **Supply chain:** pin and inventory dependencies and container images, generate an SBOM, scan and review dependencies, document reproducible/offline builds where feasible, and provide a vulnerability-reporting process. Classified network mirrors can help deliver packages but do not guarantee approval or availability.
- **Access and dissemination:** prevent public release, redistribution, export to a lower domain, or merging of differently protected guides from being implied by the tool. The organization owns authorization, handling, sanitization and release review.
- **Accessibility and resilience:** use accessible forms and output, documented backup/restore, and integrity checks. Explicitly separate a signature's technical status, trust status, authority status and policy acceptance.

## 9. Open-source licensing and governance

Recommend Apache-2.0 for OpenSCG schema, specification, examples and reference libraries, subject to legal and dependency review; its patent grant supports adoption. **Imprint application license is undecided:** the project owner is considering copyleft because integrators could reuse the application without sharing improvements. Evaluate AGPL-3.0 for Imprint, including its network-use source-offer requirement for modified versions, impact on government and integrator adoption, and compatibility with selected dependencies. AGPL does not require an integrator to contribute changes upstream or make them public to everyone, and it does not automatically cover separate systems or SCG data. The project owner is interested in retaining the option to offer Imprint under a separate commercial license to integrators who want proprietary terms; AGPL and commercial dual licensing are the leading direction, not a finalized license decision. Preserve rights to offer those terms for all covered Imprint contributions, including employer-owned work, through a counsel-reviewed contributor agreement or assignment where needed. A developer certificate of origin by itself is not an alternate-licensing grant. Third-party components retain their own license terms; public AGPL grants already made remain available under their terms. Obtain legal review before a final license choice. Retain notices and a separate trademark/branding policy. A requirement that all forks display a particular logo may conflict with standard open-source terms or adoption expectations; obtain legal review before adding custom conditions. Official releases may prominently display Knitli branding without calling a restrictive custom license Apache-2.0. The names are adopted for project planning; no trademark or domain clearance has been conducted.

OpenSCG governance and change-control requirements are specified independently in §5. Imprint has its own issue process, releases, security disclosure and contributor documentation. Provide example data with an explicit non-authoritative synthetic label. Do not copy restricted government templates or classified examples into a public repository.

## 10. Risks and unresolved decisions

| Risk or decision | Consequence | Next action / owner |
|---|---|---|
| Existing browser signing interface and agency acceptance | A configured credential may authenticate the user without exposing a document-signing operation to web content; hardware and software credentials differ. | Project and agency PKI owners identify and test the existing approved interface in each targeted browser/OS configuration; provisioning remains outside scope. |
| OCA authority and signature are conflated | A valid signature could misleadingly appear to authorize classified guidance. | Classification office defines independently reviewed delegation evidence and policy; display technical and authority outcomes separately. |
| Report attachment unavailable | The public report may not be byte-identical to the uploaded copy. | Compare against the uploaded file when accessible; findings above cite official pages. |
| Official XLSX/DTIC layout not available | An output workbook may be misleadingly described as submission-ready. | Obtain authorized template and verify fields, layout, scope and submission process with DoD/DTIC; preserve generic export label until then. |
| Content equivalence and signed representations | Matching displayed digests do not cryptographically bind a modified PDF or workbook. | Test mapping and use independently signed artifact hashes if artifact integrity is required. |
| Exemption and AEA edge cases | Invalid declassification or markings could cause operational harm. | Default to explicit unsupported/review states; agency experts review profiles before real use. |
| Classification of the guide itself and metadata | Titles, contents, logs, backups or search indexes could require protection even when source rows appear innocuous. | Deployment authority determines whole-system handling; no real data in public demo. |
| Public schedule versus actual signed capability | Access to a representative configured signing environment or acceptance review could delay feedback; claiming signing without it would mislead. | Release synthetic unsigned preview first if needed; track real signing as part of signed MVP. |
| Imprint license and contributions | Integrators may keep changes out of the upstream project; strong copyleft can add adoption and compliance friction, particularly in restricted environments. | Evaluate AGPL-3.0 for Imprint separately from permissive OpenSCG licensing; review contribution and optional commercial licensing policy with counsel. |
| Branding license | Mandatory UI branding in forks can harm open-source adoption or conflict with license terms. | Legal counsel reviews the chosen license and trademark policy. |
| Foundation choice | Large systems can impose complexity or security assumptions without solving SCG semantics. | Run a time-boxed technical spike against the minimum requirements and real offline constraints. |
| isomorphic-git evaluation | Git history can retain sensitive content and browser-backed storage may have durability limits. | Compare local Git with snapshot persistence; test recovery, access and interoperability before selection. |

**Recommendation and tradeoff:** The most complete long-term fit is a purpose-built SCG domain and approval model, kept independent of the hosting platform, with a lightweight application around it. Start by testing whether the FastAPI template reduces more work than it adds for the MVP. Corteza may reach basic collaborative workflows faster but makes the domain depend more heavily on a larger low-code platform; Mayan starts farther ahead for file control but farther behind for structured guidance. No option avoids specialist policy and signing work. The exact implementation effort is not yet measured.

**Time-boxed spike:** implement the same synthetic guide and compilation example in FastAPI and Corteza; measure initial setup, disconnected startup, schema validation, revision freeze, JSON/PDF/XLSX fidelity, integration of one local signing proof, access controls, backup/restore and dependency count. Inspect actual licenses/dependencies and security defaults. Choose the smallest platform that passes, recording prototype limits and developer effort; do not present the spike as an accreditation or finished security review.

### Suggested logical architecture

```text
Author / OCA browser (local or approved network)
  -> authoring UI + preview + review of frozen revision
  -> application service: validation + profile rules + export
  -> local draft/revision store (evaluate isomorphic-git) and protected artifact store
  -> canonical JSON + PDF + XLSX from the same frozen revision
  -> existing approved browser/workstation signing interface -> configured credential
  -> detached approval and independent verification report
```

For MVP the application can run on a workstation and persist local files; FastAPI/PostgreSQL and multi-user hosting are candidate implementation options, not requirements. In an approved shared deployment, all paths, databases, backup, keys, audit and administration remain inside the appropriate security boundary. Keep the schema, validator and exporter independent of the selected UI. Define a stable contract so another producer or consumer can implement the open format without adopting the application.
